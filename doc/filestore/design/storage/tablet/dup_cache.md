# DupCache in Filestore Tablet

Some of the POSIX requests are not idempotent - and, as a consequence, some of
the tablet's public API requests are not idempotent as well. A couple examples:
* `CreateHandle` with `O_CREAT` + `O_EXCL` flags - returns `EEXIST` if sent
  for the second time
* `UnlinkNode` - returns `ENOENT` if sent for the second time
* `RenameNode` - same story

But our system is distributed so requests need to be retried from time to time.
So we need a way to distinguish between the retries of the same request and
different requests that happen to have the same parameters. In order to do that
we have a persistent data structure called `DupCache`. `DupCache` is a mapping
between `RequestId`s and the corresponding responses. We need it to be
persistent to survive tablet restarts.

## Scope

Each session has its own `DupCache` so there's a one-to-one relation between a
client (a mount) and a `DupCache` instance. We clear session `DupCache` whenever
a session is:
* destroyed (`DestroySession` happens upon `StopEndpoint` or after
  `IdleSessionTimeout` for disconnected pipes)
* reset (`ResetSession` arrives upon mount)

## Request identification

Within a single session we fully rely on the `RequestId`s generated by the
client. In case of `virtiofs` or `FUSE` mounts it is generated by the kernel.
Technically the client can start sending duplicate `RequestId`s so our code
should not crash or arrive at an inconsistent state in this case but we still
consider such a situation to be unexpected and report critical events:
* `DuplicateRequestId`
* `InvalidDupCacheEntry`
* `DupCacheEntryRequestIdCollision`

Please grep the code to find out the details for when each of these critical
events fires.

## Entry cleanup

We delete `DupCache` entries only when we hit the per-session limit configured
via the `DupCacheEntryCount` storage config parameter - we do that upon new
entry addition. And upon session destruction/reset as mentioned earlier.

We can also drop entries which our code considers to be invalid - those can
appear only either if we have bugs in the related code or if the client
generates duplicate `RequestId`s. In this case we delete the corresponding
entries from the in-memory state only so we can end up accumulating entries with
the same `RequestId`s in the tablet's LSM. It is not an issue - such entries are
properly processed upon `LoadState` - the newest entry wins and we report a
critical event for each duplicate.

## What happens upon retry

If the transaction that created the entry is already committed, we just return
the response that's saved in `DupCache`. If it's not yet committed we return a
retriable error. The current version of the code returns `E_REJECTED`.
