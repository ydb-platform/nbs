# Пер-эндпоинтные соединения и переезд на хост таблетки в `libs/cells`

Дата: 2026-08-20
Статус: дизайн согласован, реализуется по частям

## Порядок работ

Дизайн описывает конечное состояние. Реализуется двумя инкрементами.

**Инкремент 1 — выделение соединений и проброс хоста таблетки.**
`ICellConnection` с владением и RAII-teardown, `TCellHostPool` с двумя
популяциями хостов и health, снос `ICellHost` с его автоматом, `TabletHost` в
`TMountVolumeResponse`, наблюдение за полем в виде метрик и подсказочного кэша
`diskId -> TabletHost`.

От `fix-cells-blue-green` не зависит: preemption-фиксы нужны только переезду,
который здесь не делается. Часть выигрыша по локальности приходит уже тут —
кэш направляет следующий эндпоинт того же диска сразу на хост таблетки.

**Инкремент 2 — переезд.** `SwitchEndpointToCellHost`, `OnConnectionLost`,
работа со `SwitchSession`, откат при частичном отказе, гонки с релокацией.
Требует раскатанного `fix-cells-blue-green` на обеих ячейках.

## Контекст

`cloud/blockstore/libs/cells` реализует шардирование control plane. Сервер
принадлежит одной ячейке и знает про остальные; при старте эндпоинта он веером
рассылает `DescribeVolume` по всем ячейкам плюс себе, а дальше работает с той,
что ответила.

Сегодня соединения к хостам чужих ячеек переиспользуются между клиентами:

- **gRPC** — один `IMultiClientEndpoint` на (хост, порт).
  `CreateClientEndpoint(clientId, instanceId)` возвращает лишь фасад,
  проставляющий заголовки поверх общего канала.
- **RDMA** — `CreateRdmaDataEndpointAsync` создаёт **один** `IBlockStorePtr` на
  хост при активации, и он отдаётся всем клиентам как есть. Пер-клиентского
  понятия нет вовсе.

Оба создаются жадно в `TCellHost::Start()`, до того как хоть кто-то что-то
смонтировал. Отсюда растут остальные проблемы: `ICellHost::Stop()` возвращает
пустой future и teardown отсутствует как таковой (закрывать общее соединение
некому); изоляции отказов нет; на серверной стороне одна RDMA-сессия
обслуживает много клиентов.

Кроме того, монтирование тома всегда уходит по gRPC, даже для RDMA-ячеек. Не
потому, что RDMA этого не умеет — умеет с обеих сторон, message id совпадают, —
а потому что способность отбрасывается: `CreateRemoteStorage` сужает
полноценный `IBlockStorePtr` до `IStorage`, у которого нет ни `MountVolume`, ни
`UnmountVolume`.

## Цели

1. Соединение с данными принадлежит одному поднятому эндпоинту и умирает
   вместе с ним.
2. Появляется работающий teardown вместо нынешнего его отсутствия.
3. Эндпоинт работает с тем хостом, где реально живёт таблетка тома, без лишнего
   сетевого хопа внутри чужой ячейки.
4. Отказ хоста не убивает эндпоинт.
5. Всё это раскатывается на две ячейки без простоя и без поломок в промежуточных
   состояниях.

## Вне рамок

- Перенос mount/unmount на RDMA. Способность есть с обеих сторон, но
  сегодня она отбрасывается адаптером; трогать это здесь не будем.
- Разделение `libs/cells` на несколько библиотек.
- Устранение дублирования протокола (`NClient::TBlockStoreProtocol` и
  `NStorage::TBlockStoreServerProtocol` объявляют один провод дважды).

## Принятые решения

| Вопрос | Решение |
|---|---|
| Гранулярность соединения | один поднятый эндпоинт (`StartEndpoint`) |
| Какие каналы пер-эндпоинтные | только data; control-gRPC остаётся пулом на хост |
| Отказ data-соединения | прозрачный перевыбор хоста |
| Транспорты | единообразно для RDMA и gRPC |
| Переезд на хост таблетки | на каждом ремаунте, если хост сменился |

Control-канал оставлен в пуле потому, что gRPC-фасад ничего не стоит и ничего
не изолирует, а по нему ходит мало: `MountVolume` (включая периодический
ремаунт по `ScheduleVolumeRemount`), `UnmountVolume`, `ExecuteAction`. Данные —
`ReadBlocksLocal`, `WriteBlocksLocal`, `ZeroBlocks` — идут через `IStorage`.
Разводит их `TStorageDataClient` в `session_manager`.

## Архитектура

### Почему переезд нельзя спрятать в `libs/cells`

Сервисный узел валидирует сессию **локально**, до форвардинга
(`service_actor_forward.cpp`): нет тома в `State` — `E_BS_INVALID_SESSION
"volume not found"`, нет клиента — то же, не совпал `SessionId` — то же.

Значит переткнуть только data-канал на хост таблетки нельзя: он про эту сессию
не знает. Переезд — всегда ремаунт, а монтированием владеет `TSession`, которая
живёт выше слоя ячеек. Отсюда разделение: **`libs/cells` владеет соединениями и
здоровьем хостов, `session_manager` — решением о переезде**, потому что владеет
сессией и собирает клиентский стек (validation, throttling, encryption,
durable, data-integrity), о котором ячейки знать не должны.

### Интерфейсы

```cpp
struct ICellManager: IStartable
{
    TDescribeVolumeFuture DescribeVolume(...);          // без изменений

    // fqdn пустой -> выбрать живой конфигурационный хост
    TResultOrError<ICellConnectionPtr> CreateConnection(
        const TString& cellId,
        const TString& fqdn,
        const NClient::TClientAppConfigPtr& clientConfig,
        ICellConnectionObserverPtr observer);
};

struct ICellConnection
{
    virtual ~ICellConnection() = default;

    virtual TString GetHost() const = 0;
    virtual IBlockStorePtr GetService() const = 0;   // control, из пула
    virtual IStoragePtr GetStorage() const = 0;      // data, своё
};

struct ICellConnectionObserver
{
    virtual void OnTabletHostChanged(TString fqdn) noexcept = 0;
    virtual void OnConnectionLost() noexcept = 0;
};
```

Наблюдатель — единственный канал наружу. Оба события ведут к одному действию,
отличается лишь выбор цели: в первом случае она названа, во втором её берут из
конфигурационной популяции.

### Компоненты `libs/cells/impl`

**`TCellHostPool`** — один на ячейку, единственный носитель состояния. Держит
control-каналы по FQDN, ведёт health, отвечает на «дай живой хост». Две
популяции хостов:

- *конфигурационные* — из `TCellConfig.Hosts`, тёплые, health-check. Нужны для
  дескрайбов и как **гарантированная точка повторного входа** в ячейку;
- *хосты таблеток* — узнаются из `TabletHost` в ответах на монтирование,
  заводятся по требованию, живут по refcount соединений.

Подключиться ко второй популяции возможно потому, что порты в
`TCellHostConfig` берутся из `TCellConfig`, а не задаются на хост: FQDN из
ответа плюс порты ячейки — достаточно.

Пул также держит подсказочный кэш `diskId -> последний известный TabletHost`.

**`TCellConnection`** — на поднятый эндпоинт. Берёт control-канал из пула,
заворачивает его так, чтобы видеть ответы на `MountVolume`, создаёт
собственный data-канал, сравнивает `TabletHost` со своим FQDN и дёргает
наблюдателя.

Дескрайбы ходят в пул напрямую — им data-канал не нужен.

### Что удаляется

`ICellHost` вместе с конечным автоматом и мёртвыми ветками `Stop`/`DEACTIVATING`
(`State` сегодня никогда не становится `ACTIVE`, `DeactivatingHosts` никогда не
наполняется, `StopPromise` никогда не выставляется); четыре коллекции хостов в
`TCell`; `TCellHostEndpoint` как возвращаемое значение;
`GetStrictCellIdCheckInDescribeVolume` (объявлен, не определён, не вызывается).

`TRemoteStorage` остаётся — он по-прежнему нужен как адаптер data-канала.

### Изменения в `session_manager`

`TEndpoint` дополнительно держит `ICellConnectionPtr`. `TSessionManager`
реализует `ICellConnectionObserver`; оба колбэка только кладут задачу в
`Executor`. Появляется приватный `SwitchEndpointToCellHost(socketPath, fqdn)` —
сосед существующего `SwitchSessionForEndpoint`, который уже делает то же самое
для релокации тома.

Переключение выполняется через существующий `ISwitchableSession`, который уже
безусловно стоит в `CreateEndpoint` для каждого эндпоинта. Это не «клиента
подменить»: он меняет сессию целиком, дренирует старую и — самое ценное —
перенаправляет ретраи старых запросов из старого `DurableClient` в новый стек.
Смена `SessionId` там предусмотрена параметром.

## Потоки

### Старт эндпоинта (том в чужой ячейке)

1. `CreateSessionImpl` → `DescribeVolume` через пул → непустой `CellId`.
2. `CreateConnection(cellId, подсказка_из_кэша_или_пусто, ...)`.
3. `TStorageDataClient` над парой `GetService()`/`GetStorage()`, дальше стек и
   сессия без изменений. `ForceRemoteBinding = true`, так как `cellId` непуст.
4. `ICellConnectionPtr` кладётся в `TEndpoint`.

Локальный том (`CellId` пуст) слой ячеек не задевает вовсе.

Хост таблетки узнаётся только из ответа на монтирование, поэтому без кэша при
`N` живых хостах старт с вероятностью `(N-1)/N` превращается в два
монтирования и переключение. Кэш подсказочный: промах не ломает ничего, просто
возвращает двойное монтирование.

### Переезд на хост таблетки

1. Обёртка видит `TabletHost = T` ≠ свой FQDN → `OnTabletHostChanged(T)`.
2. Наблюдатель кладёт задачу в `Executor`; в колбэке фьючи не делается ничего,
   иначе переключение произойдёт посреди обработки `TSession` собственного
   ответа на монтирование.
3. Задача перепроверяет состояние: эндпоинт жив, переезд не идёт, мы не на T.
4. `CreateConnection(cellId, T, ...)` → новый стек → новая `TSession`.
5. Монтируемся новой сессией — это регистрирует том и сессию на сервисе T.
6. `SwitchSession(diskId, newSessionId, newSession, newSwitchableClient)`.
7. Отпускаем старый `ICellConnection`.

Неудача на шаге 5 обработки не требует: остаёмся на месте, следующий ремаунт
принесёт `TabletHost` снова. Период ремаунта работает естественным backoff.

Если во время переезда таблетка уехала ещё раз, монтирование на T всё равно
удастся (T привяжется к ней удалённо), а его ответ принесёт новый `TabletHost` —
схема сходится без специальной обработки.

### Отказ хоста

Тот же путь, цель берётся из конфигурационной популяции. Обнаруженные хосты как
замену брать бессмысленно: они привязаны к таблеткам, которых там может уже не
быть.

Смерть хоста не тупик. Если умер хост таблетки, hive поднимет её в другом месте;
мы перемонтируемся через конфигурационный хост, он привяжется к таблетке на
новом месте, в ответе придёт новый `TabletHost`, и дальше обычный переезд. Окно,
пока hive перезапускает таблетку, закрывается существующими retriable-ответами
из `service_actor_forward.cpp` (`State == INITIAL`, `State != STARTED`).

Триггер идёт **от пула, а не от соединения**: у RDMA-клиента есть собственный
реконнект, и переезжать надо не на каждое моргание, а когда хост признан
мёртвым.

### Остановка

`RemoveSession` → сессия размонтируется → `TEndpoint` разрушается →
`ICellConnectionPtr` отпускается → data-канал закрывается по мере ухода
in-flight, счётчик ссылок на control-канал уменьшается. Обнаруженный хост с
нулевым счётчиком выбрасывается из пула, конфигурационные остаются тёплыми.

## Краевые случаи

**Пустой `TabletHost`** — не переезжаем никогда. Это же правило служит признаком
готовности удалённой ячейки (см. раскатку).

**Флаппинг таблетки.** Политика «на каждом ремаунте» означает до одной подмены
сессии за период ремаунта, если hive перебалансирует том туда-сюда.
Предохранители без изменения политики: не начинать переезд, если он уже идёт, и
считать неудачу «остались на месте». Нужен счётчик переездов на эндпоинт, чтобы
флаппинг был виден.

**Гонки.** Все задачи идут через `Executor` и потому сериализованы, но задача
переезда обязана перепроверять состояние в момент исполнения, а не доверять
захваченным значениям: эндпоинт мог быть удалён; релокация могла сменить
`diskId` через `SwitchSessionForEndpoint`; мы могли уже переехать.

**Частичный отказ.** Единственное место, требующее явного отката: монтирование
на новом хосте прошло, а `SwitchSession` не удался. Тогда живых монтирований
два — новую сессию размонтировать, остаться на старой.

**Время жизни соединения во время дренажа.** После `SwitchSession` старая сессия
ещё дренируется и её стек продолжает пользоваться старыми `IStorage`/
`IBlockStore`. Поэтому объекты, возвращаемые `GetStorage()`/`GetService()`,
обязаны сами держать `shared_ptr` на `ICellConnection`. Владение — по факту
использования, а не по факту хранения; отпускание хэндла наверху безопасно.

**`ForceRemoteBinding` на целевом хосте.** Переехав на T, продолжаем слать
`ForceRemoteBinding = true`. Сервис на T привяжется к таблетке, живущей на нём
же, удалённо через пайп: лишнего сетевого хопа нет, а таблетка не пришпиливается
нашим монтированием. Записано явно, чтобы флаг не «оптимизировали» на целевом
хосте.

## Совместимость и раскатка

Ячеек две, каждая одновременно клиент другой; атомарно переключить обе нельзя.
Любое изменение должно быть безопасно во всех четырёх сочетаниях старый/новый ×
клиент/сервер.

Через границу ячеек ходят: `DescribeVolume` с `Headers.CellId` (есть сейчас),
`MountVolume.ForceRemoteBinding` (в ветке `fix-cells-blue-green`, не раскатано),
`TMountVolumeResponse.TabletHost` (добавляем; сегодня такого поля нет — есть
аналогичное в `TStatVolumeResponse`), данные (провод не меняется).

Деградация безопасна сама по себе: старый сервер игнорирует неизвестное
`ForceRemoteBinding` и считает привязку по-старому; старый сервер не проставит
`TabletHost`, а правило «пусто — сиди где сидишь» делает переезд
самоотключающимся.

Переезд требует preemption-фиксов **на принимающей стороне** — иначе `AddClient`
с нового пайпа при живом старом будет выбивать сессию. Проверку версий заменяем
трюком: **`TabletHost` сам служит признаком готовности**, так как его выставляет
только код, содержащий эти фиксы. Условие — никогда не выпускать поле раньше их.

Отсюда жёсткий порядок:

1. `fix-cells-blue-green` смержен и раскатан на обе ячейки.
2. Серверная часть: `TabletHost` в `TMountVolumeResponse` плюс конфиги приёма
   (`Backlog`, `PollerThreads`). Инертно, читателей ещё нет.
3. Клиентская часть: пер-эндпоинтные соединения и переезд, под флагом в конфиге
   ячеек, по умолчанию выключено.
4. Включение по ячейкам с раскачкой.

Шаги 2 и 3 нельзя менять местами, иначе признак готовности перестаёт работать.

### Цена соединения на принимающей стороне

Память — не проблема. На сессию пиннятся два буфера:
`SendQueueSize * sizeof(TResponseMessage)` и
`RecvQueueSize * sizeof(TRequestMessage)`, а `RDMA_RESPONSE_SIZE = 16` и
`RDMA_REQUEST_SIZE = 64`. При `QueueSize = 10` это 800 байт на сессию. Буферы
данных берутся из общего пула на время запроса и возвращаются, то есть
масштабируются от конкурентности, а не от числа соединений.

Реальные ограничители:

- **дескрипторы** — у каждой сессии свой completion channel;
- **поллер** — `PollerThreads = 1` по умолчанию, а цикл на каждой итерации
  обходит все сессии поллера; стоимость линейна по их числу;
- **потолка нет вообще** — ни на число сессий, ни на inflight
  (`MaxInflightBytes = Max<ui64>()`).

`Backlog = 10` — это очередь `rdma_listen` для необслуженных запросов на
подключение, не потолок установленных сессий. Поднять его стоит, но по другой
причине: наша схема порождает всплески подключений при массовом рестарте.

Отдельный потолок на число соединений к хосту пока не закладываем: узкое место —
поллер, и правильный ответ на него `PollerThreads`. Если окажется мало, добавим
по метрикам.

## Наблюдаемость

Минимум, без которого нельзя выкатывать: число соединений в разрезе
ячейка/хост, переезды и их неудачи на эндпоинт, доля времени на не-таблеточном
хосте, состояние health по хостам.

Складывать это в страницу «Cells», у которой `TCellManager::OutputHtml` сейчас
пустой — страница зарегистрирована и не показывает ничего.

## Тестирование

Опора — существующий шов `ICellHostEndpointBootstrap`: интерфейс сделан ровно
затем, чтобы подсовывать фейковые эндпоинты вместо gRPC/RDMA.
`describe_volume_ut.cpp` должен продолжать проходить без изменений.

**Пул.** Канал к FQDN, которого нет в конфиге; refcount обнаруженных хостов
(выбрасываются на нуле, конфигурационные остаются); мёртвый хост исключается из
выдачи; кэш `diskId -> TabletHost` влияет на выбор и промах безвреден.

**`TCellConnection`.** Data-канал создаётся на соединение и закрывается при
отпускании; control берётся из пула; `OnTabletHostChanged` поднимается только
при непустом и отличном от своего FQDN.

**Оркестрация переезда** — с фейковым `ICellManager` в `session_manager_ut.cpp`:
переезд при смене хоста; повторные уведомления дают один переезд; протухшая
задача отбрасывается после удаления эндпоинта или смены `diskId`; отказ после
успешного нового монтирования оставляет старую сессию; старое соединение
переживает дренаж.

**Уровень акторов** — в стиле `service_ut_mount.cpp` на двух узлах:
монтирование через A с `ForceRemoteBinding`, ремаунт на B с таблеткой,
переключение, сессия не потеряна. Сосед добавленного в blue-green
`ShouldPreserveBlueGreenHandoffThroughRemoteBindings`.

**Совместимость** — пустой `TabletHost` не вызывает переезда никогда.

**Не покрывается юнит-тестами:** поведение при сотнях соединений на хост —
обход сессий поллером, расход дескрипторов, всплески подключений. Это стенд и
нагрузка, и именно это гейтит включение флага.

## Риски

1. Схема зависит от `fix-cells-blue-green`. До его раскатки на обе ячейки
   переезды включать нельзя.
2. Переезд на каждом ремаунте при флаппинге таблетки даёт подмену сессии за
   период ремаунта. Политика выбрана осознанно; если метрики покажут проблему,
   вводится гистерезис.
3. Рост числа соединений бьёт по принимающей стороне, которая в момент
   раскатки может быть на старом релизе со старыми `Backlog`/`PollerThreads`.
   Смягчается порядком шагов 2 и 3.
