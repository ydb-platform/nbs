# Приём межъячейковых control-запросов в `libs/cells`

## Контекст

Соединение ячейки форвардит `Mount`/`Unmount`/`Describe` на хост чужой ячейки по
gRPC. Авторизация этих запросов на принимающей стороне сейчас не продумана, и
это дыра в двух смыслах.

Токен на исходящем запросе берётся не из заголовков, а из статического конфига
gRPC-клиента: `client.cpp:440` кладёт в metadata `authorization` значение
`AppCtx.Config->GetAuthToken()`. Пер-реквестный (пользовательский) токен через
этот клиент передать нельзя в принципе — клиент один на пул. При этом ни токена
ячейки, ни mTLS у нас нет. Принимающая сторона токен берёт **только** из metadata
gRPC на `SOURCE_SECURE_CONTROL_CHANNEL` (`server.cpp` `ValidateRequest`,
`GetAuthToken`), а тело `Internal` — где живут `AuthToken` и `RequestSource` —
сервер у клиента отвергает вовсе (`server.cpp:713`, `E_ARGUMENT`). Значит протащить
исходный пользовательский токен нельзя ни телом, ни этим клиентом.

Сегодняшнее следствие: `Mount`/`Unmount`/`Describe` несут непустой список прав
(`auth_scheme.cpp`, `UnmountVolume` → `Update` и т.д.), поэтому
`NeedAuth == true` (`auth_provider_kikimr.cpp:207`), а токен пустой — то есть
межъячейковый форвард на авторизации бы падал.

Принято смириться с этим по-другому: **авторизация случается на входном узле**, а
межъячейковый хоп — доверенная внутрикластерная пересылка, которую повторно
авторизовывать не надо. Ровно так уже устроен data channel: он IAM-авторизацию не
проходит (`auth_provider_kikimr.cpp:205` — *«Data channel does not need IAM
authorization: all requests are allowed if authorized with mount tokens»*). Нужен
такой же доверенный путь для трёх control-операций.

## Цели

`Mount`/`Unmount`/`Describe`, пришедшие из другой ячейки по доверенному каналу,
исполняются в обход `AuthService`. Остальной трафик авторизуется как раньше.

Страница ячеек перестаёт быть заглушкой и показывает три вещи: дамп конфига,
поиск диска по ячейкам (по образцу `storage/service`) и межъячейковые
подключения — сколько на хосте активно и от кого.

## Вне рамок

- Авторизация на входном узле — не меняется, она и есть источник истины.
- Пробрасывание пользовательского токена на хост ячейки — архитектурно
  невозможно текущим gRPC-клиентом и не нужно при доверенной модели.
- Строгий учёт «открытие/закрытие» соединения. `Unmount` не гарантирован (клиент
  мог упасть, соединение — переехать), поэтому парный счётчик протекал бы; см.
  «Наблюдаемость».
- Замена модели доверия. Вся схема стоит на «secure-порт доступен только из
  underlay»; это допущение, а не то, что вводится здесь.

## Принятые решения

1. **Доверие берётся из канала, а не из заголовка.** `ERequestSource`
   штампуется сервером по слушающему порту (`server.cpp:1073-1114`: insecure-порт
   → `SOURCE_INSECURE_CONTROL_CHANNEL`, secure-порт →
   `SOURCE_SECURE_CONTROL_CHANNEL`) и подделать его клиент не может. `CellId` —
   обычный заголовок, клиентский, поэтому сам по себе доверия не несёт. Пропуск
   авторизации разрешён только на `SOURCE_SECURE_CONTROL_CHANNEL`.

2. **`CellId` — маркер намерения, не привилегия.** `CellId` уже несёт смысл
   «из какой/в какую ячейку» (`headers.proto:103`, ставится в
   `describe_volume.cpp:269`, проверяется на consistency в `server.cpp:738`).
   Навешивать на это же поле «не авторизовывать» — значит смешать идентичность и
   привилегию: любой будущий код, выставивший `CellId` по routing-причине, молча
   снял бы авторизацию. Поэтому решение о пропуске принимает **отдельный сервис**,
   а `CellId` остаётся идентификатором и лишь служит признаком «это форвард».

3. **Гейт — конъюнкция трёх условий.** Запрос идёт в обход `AuthService` тогда и
   только тогда, когда `source` — доверенный серверно-проставленный источник
   **и** в заголовках выставлен `CellId` **и** тип запроса из белого списка
   `{DescribeVolume, MountVolume, UnmountVolume}`. Всё в `AND`: маркер инертен на
   любом недоверенном пути, а белый список ограничивает радиус поражения. Для
   gRPC доверенный источник — это `SOURCE_SECURE_CONTROL_CHANNEL` (штампуется по
   порту); это заодно отсекает локальный describe с меткой `"local"` — он не идёт
   по secure-gRPC. Множество доверенных источников расширяемо — см. решение 5.

5. **Транспорт-независимость.** `CellForwardService` — единая точка приёма
   межъячейкового control, и она обязана стоять перед сервисом, в который
   диспетчеризует **любой** транспорт, а не только gRPC-стек. Сейчас control идёт
   только по gRPC, но rdma-эндпоинт рано или поздно понесёт `Mount`/`Unmount`
   тоже; когда это случится, rdma-серверный эндпоинт должен диспетчеризовать в тот
   же `CellForwardService`, что и gRPC. Отсюда важное: доверие в решении 3 нельзя
   зашивать в один `SOURCE_SECURE_CONTROL_CHANNEL` — у rdma этого источника нет, и
   запрос по rdma провалился бы в `Authorized` с пустым токеном. Гейт проверяет
   *множество* доверенных серверно-проставленных источников; rdma-серверный
   эндпоинт стамповать свой (напр. `SOURCE_RDMA_CONTROL_CHANNEL`), на том же
   допущении про underlay-изоляцию, что и secure-порт.

4. **Реализация — декоратор `IBlockStore` в `libs/cells`.** `AuthService` сам
   является таким декоратором (`service_auth.cpp:20`), и в стеке уже есть
   прецедент доверенного обхода авторизации — `udsService` захватывается по ссылке
   *до* `InitAuthService` (`bootstrap.cpp:726` против `:740`), поэтому трафик
   unix-сокета в auth не заходит. Наш сервис — тот же приём в явном виде: он держит
   две ссылки и разводит запрос в одну из них. Вся серверная логика ячеек живёт в
   `libs/cells`, daemon только инстанцирует — как уже с `CellManager`.

## Архитектура

### Форма и размещение

Новый фабричный метод в `cells/iface` (рядом с `cell_manager.h`, ту же границу
видимости daemon уже использует), реализация — в `cells/impl`.

```cpp
// cells/iface: объявление
IBlockStorePtr CreateCellForwardService(
    IBlockStorePtr authorized,     // путь через AuthService
    IBlockStorePtr trusted,        // сервис под AuthService, без авторизации
    IMonitoringServicePtr monitoring,
    ILoggingServicePtr logging);
```

`authorized` и `trusted` указывают на один и тот же внутренний стек; разница в
одном слое `AuthService` между ними. Для каждого запроса сервис вычисляет гейт из
решения 3 и форвардит в `trusted` при выполнении, иначе в `authorized`.

```
                      ┌─ гейт выполнен ─→ trusted   (Describe/Mount/Unmount,
                      │                              авторизовано выше)
request → CellForward ┤
                      └─ иначе ─────────→ authorized → AuthService → …
```

### Проводка в daemon

По образцу `udsService`, вокруг `InitAuthService` (`bootstrap.cpp:740`):

```cpp
auto trusted = Service;                       // до навешивания auth
InitAuthService();                            // Service := AuthService(trusted)
if (Configs->CellsConfig->GetCellsEnabled()) {
    Service = NCells::CreateCellForwardService(
        Service,                              // authorized
        trusted,
        Monitoring,
        Logging);
}
// дальше внешние слои (validation, throttling, …) оборачивают Service
```

Важно, что `CellForward` встаёт **сразу снаружи** `AuthService`, а не в самом
верху: внешние слои (валидация, throttling) должны применяться к межъячейковым
запросам тоже — пропускается ровно и только авторизация.

### Оба транспорта

`CellForwardService` — это сервис, в который диспетчеризует приёмная сторона,
поэтому его же надо передавать не только в gRPC-стек, но и в rdma-серверный
эндпоинт, когда тот начнёт нести control. Пока control по rdma не ходит, правка
сводится к тому, чтобы rdma-эндпоинт на приёме конструировался поверх того же
`Service`, что и gRPC, — тогда добавление `Mount`/`Unmount` по rdma не потребует
второго места с политикой доверия. Соответствующий серверно-проставленный source
(решение 5) вводится вместе с control-over-rdma, не раньше.

### Гейт

Источник и заголовки к моменту стека уже подготовлены сервером: `ValidateRequest`
→ `PrepareRequestHeaders` проставляет `Internal.RequestSource` по порту до входа в
сервисный стек, а `CellId` — обычный заголовок, сервер его не срезает (в отличие
от `Internal`). Значит декоратор читает и то и другое как есть.

```cpp
template <typename TMethod>
TFuture<typename TMethod::TResponse> Execute(ctx, request)
{
    const auto& headers = request->GetHeaders();
    const bool trusted =
        IsWhitelisted(TMethod::BlockStoreRequest) &&      // Describe/Mount/Unmount
        IsTrustedSource(headers.GetInternal().GetRequestSource()) &&
        !headers.GetCellId().empty();

    RecordActivity(TMethod::BlockStoreRequest, headers);  // см. «Наблюдаемость»

    auto& target = trusted ? Trusted : Authorized;
    return TMethod::Execute(target.get(), std::move(ctx), std::move(request));
}
```

Белый список — статический, три метода. Для всех прочих `TMethod` гейт ложен по
первому условию, и они всегда идут в `Authorized` — независимо от `CellId` и
source.

### Правка в самой ячейке

Соединение сейчас `CellId` на control-запросах **не ставит** — только
`describe_volume` (`describe_volume.cpp:269`), в `connection.cpp` `SetCellId` нет.
Чтобы гейт срабатывал, `TControlService` соединения должен штамповать `CellId`
своей ячейки на `Mount`/`Unmount` (аналогично тому, как `describe_volume`
проставляет его на describe). Это единственная правка на стороне клиента ячейки.

## Наблюдаемость

Страница ячеек уже существует: `TCellsMonPage` → `TCellManager::OutputHtml`
(`cell_manager_impl.cpp:36`, `:181`), зарегистрирована под `Cells` в индексной
странице blockstore (`:67`), но сейчас `OutputHtml` — заглушка (`Y_UNUSED`). Она
и становится домом для трёх разделов: дамп конфига, поиск диска, межъячейковые
подключения. Всё рисуется в `OutputHtml`, диспетчеризация по `action` из
параметров запроса — как в `storage/service` (`service_actor_monitoring.cpp:96`,
таблицы `getActions`/`postActions`).

### Дамп конфига

`OutputHtml` печатает текущий `TCellsConfig`: список ячеек, их хосты и порты
(`GrpcPort`/`SecureGrpcPort`/`RdmaPort`), флаги (`HostMigrationEnabled`,
`GrpcDataFallbackEnabled`, периоды пинга и т.д.) и параметры gRPC-клиента.
Конфиг — proto, поэтому проще всего рендерить таблицей поверх
`GetCells()`/`GetGrpcClientConfig()`; сырой `DebugString()` допустим как первый
шаг. Это статический раздел, без действий.

### Поиск диска

По образцу `storage/service` (`service_actor_monitoring_search.cpp`,
`THttpFindVolumeActor`): форма `BuildSearchButton`-стиля с
`action=search&Volume=<diskId>`, диспетчеризуемая в `OutputHtml`. Обработчик зовёт
уже существующий `TCellManager::DescribeVolume(diskId)`
(`cell_manager.h:36`) и печатает, в какой ячейке/на каком хосте живёт диск (из
`GetCellId()` ответа), либо ошибку/`not found`.

Отличие от `storage/service` — там поиск живёт в актор-системе (`SSProxy`,
`TActorBootstrapped`), а ячейки на фьючерах и без акторов. Поэтому обработчик не
плодит актор, а ждёт `TDescribeVolumeFuture` с таймаутом прямо в рендере
(`OutputContent` пишет в поток синхронно); таймаут берётся из конфига gRPC-клиента.

### Межъячейковые подключения

Данные приходят с **принимающей** стороны — из `CellForwardService`, который
единственный видит входящие `Mount`/`Unmount`/`Describe`. Строгий парный учёт
(`Mount` ++ / `Unmount` --) отвергнут: `Unmount` не гарантирован, счётчик
протекал бы. Вместо этого сервис держит таблицу **последней активности**, ключ
`(CellId, peer, diskId, clientId)`: на каждом запросе обновляется `LastSeen` и
инкрементится счётчик по типу. Раздел показывает записи с недавним `LastSeen`;
протухшие вычищаются по TTL. Это даёт «кто сейчас на мне активен из ячеек» без
зависимости от парности.

Проводка: `CellForwardService` отдаёт снапшот этой таблицы (узкий метод-геттер),
а страница его печатает. `CellForwardService` и `TCellsMonPage` — разные объекты
(приём против исходящих соединений узла), но на одном узле; связывать их надо
именно снапшотом, а не общим состоянием под локом. Альтернатива — сервис
регистрирует собственный под-раздел; выбор за реализацией.

Отдельно — counters: число межъячейковых `Mount`/`Unmount`/`Describe`, разрез по
`CellId`.

### Аудит

Раз на доверенных запросах авторизация выключается, каждый такой пропуск логируется
(`request`, `CellId`, `peer`, `diskId`) — чтобы постфактум был след, кто чем ходил
в обход `AuthService`.

## Безопасность

**Допущение, на котором держится всё:** secure control-порт доступен только из
underlay. Тогда обычному заголовку `CellId` на этом канале можно верить, потому что
выставить его может лишь узел внутри доверенного периметра. Это допущение должно
быть зафиксировано письменно; если периметр secure-порта когда-нибудь ослабнет,
пропуск авторизации `Mount`/`Unmount` станет прямым обходом.

**Признак пришёл не из доверенного источника** (`CellId` есть, но `source` не в
множестве доверенных) — это либо ошибка конфигурации, либо попытка подделки;
такой случай логируется как предупреждение/алерт и, разумеется, идёт в
`Authorized` (гейт по source ложен). Множество доверенных источников — единое
место, откуда добавляется rdma; расширять его — сознательное security-решение, не
побочный эффект.

**Наименьшие привилегии.** Белый список — три метода, не «любой запрос с
`CellId`». Поверхность обхода авторизации = один сервис в `libs/cells`; полный её
список берётся `grep`-ом по фабрике, а не размазан по трактовке `CellId`.

## Тестирование

- `source == SECURE` + `CellId` + `Mount` → ушёл в `trusted`, `AuthService` не
  вызывался.
- `source == SECURE` + `CellId` + не-whitelisted метод → в `authorized`.
- `source == SECURE` + `CellId` пуст → в `authorized`.
- `source == INSECURE` + `CellId` + `Mount` → в `authorized` (source не тот),
  плюс сработал алерт про подозрительный признак.
- прочий трафик без `CellId` → в `authorized` при любом source.
- наблюдаемость: `Mount` от ячейки заводит/обновляет запись `(CellId, peer, …)`,
  протухание по TTL её убирает.
- ячейка: `Mount`/`Unmount` от соединения несут `CellId` своей ячейки.
- страница: `OutputHtml` печатает разделы конфига и подключений (не заглушка).
- поиск: `action=search&Volume=<diskId>` возвращает ячейку/хост диска через
  `DescribeVolume`; несуществующий диск → `not found`, а не падение; таймаут
  фьючера отрисовывается как ошибка, не виснет.

## Риски

**Слишком широкий гейт.** Ошибка в белом списке или потеря условия по source
превращает сервис в универсальный обход авторизации. Смягчение — конъюнкция из
трёх условий с обязательным server-stamped source и явный тест на каждую ветку.

**Протухание таблицы активности.** TTL подобран неверно — либо показываем
мёртвые подключения, либо теряем живые. Величина TTL кратна периоду, с которым
ячейка перемонтируется/пингует; настраивается одним полем.

**Связанность с раскаткой ячеек.** Сервис навешивается только при
`GetCellsEnabled()`; при выключенных ячейках стек не меняется вовсе.
