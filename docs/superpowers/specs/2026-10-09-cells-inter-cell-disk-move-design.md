# Переезд диска между ячейками

Дизайн. Рабочий журнал с разбором кода и шестью кругами ревью — в
`2026-10-09-cells-inter-cell-disk-move-plan.md`; здесь только итог: что
строим и почему именно так.

## Контекст

Диск можно перенести на другой носитель внутри ячейки — это linked volumes
(`doc/blockstore/storage/changing-media-type.md`). Рядом с диском `id`
создаётся `<id>-copy` с тегом `source-disk-id`, таблетка лидера переливает
данные в фоне и зеркалирует живые записи, потом передаёт лидерство копии;
клиент узнаёт об этом из `PrincipalDiskId` в ответе на remount и переключает
сессию. Источник удаляется. Простоя у клиента нет.

Между ячейками так нельзя: каждый шаг linked volumes ходит в локальные
SSProxy, volume proxy и storage service, а `libs/cells`, который умеет
говорить с чужой ячейкой, доступен только из слоя daemon и endpoint'ов — до
акторов томов он не достаёт.

Переезд между ячейками сегодня есть только у Disk Manager: копирование по
чекпоинтам через gRPC, в конце заморозка источника и последняя итерация.
Тома друг о друге не знают, живые записи не зеркалируются, на последнюю
итерацию есть простой. Этот путь остаётся под флагом как запасной.

## Цели

Переезд диска из ячейки A в ячейку B внутри зоны тем же механизмом, что и
внутри ячейки: без простоя, с зеркалированием записей, с переключением
клиента по `PrincipalDiskId`. Инициатор — приватная операция Disk Manager.
Compute про ячейки не знает и этой операции не видит.

## Вне рамок

- Клонирование: независимая копия с сохранением источника.
- Решение, какой диск куда везти.
- Авторизация межъячеечных запросов. Новые запросы идут по доверенному
  каналу без неё, как сегодня `Mount`/`Unmount`/`Describe`. Что из этого
  следует — в «Рисках».
- Переименование тома в NBS. Диск после переезда физически называется
  `<id>-copy`; внешнее имя сохраняет DM.

## Как это работает

```
DM (приватный rpc MigrateDiskBetweenCells)
  1. attempt token t
  2. Clone: <id>-copy в B, теги source-disk-id и attempt=t, тот же EncryptionDesc
  3. FinishFillDisk
  4. CreateVolumeLink в A: follower = <id>-copy в B, LinkUUID = t
  5. ждать getlinkstatus в A == LEADERSHIP_TRANSFERRED
  6. ждать: на A ноль клиентов, прошло >= InactiveClientsTimeout, B виден
  7. удалить A; alias id -> <id>-copy; снять тег attempt с B

NBS, таблетка лидера в A
  describe follower в B      через мост
  link на follower в B       через мост, UpdateVolumeLink
  данные на follower в B     через мост, copy-volume-client без маунта
  передача лидерства         как внутри ячейки, плюс drain перед рубежом

Клиент
  remount -> PrincipalDiskId + PrincipalCellId -> сессия на B
```

## Решения

### 1. Внешнее имя хранит DM, физическое чередуется

Linked volumes требуют разных имён для лидера и follower'а, а переименования
в NBS нет. Поэтому после переезда диск физически называется `<id>-copy`, а
DM хранит в записи диска постоянное поле физического имени и подставляет
его во все вызовы NBS. Compute продолжает знать диск под `id`.

Повторный переезд не наращивает суффикс, а чередует имя `id → <id>-copy →
id`. NBS так уже устроен: `GetNextDiskId` делает ровно это, а всё, что
смотрит на `GetLogicalDiskId` (статистика, destroy, менеджер сессий),
считает `id` и `<id>-copy` одним логическим диском — третьего имени туда
не вписать. Безопасно, потому что источник удаляется до конца переезда и
его имя снова свободно.

Внешний ID, сам оканчивающийся на `-copy`, в этот путь не допускается:
`GetNextDiskId(foo-copy)` вернёт `foo` и склеит его с чужим диском. DM
отвергает такой запрос на входе.

### 2. Клиент находит диск и после удаления A

Compute Node стартует endpoint по `id`, DM в этом пути не участвует. Пока A
жив, его таблетка редиректит клиента на `<id>-copy`; после удаления A
редиректить некому. Две ситуации, два средства в NBS:

- **A жив, лидерство передано.** `DescribeVolumeResponse` от A заполняет
  `PrincipalDiskId` (сегодня он приходит только в ответе на mount) и новое
  поле `PrincipalCellId`. Переключение сессии идёт в эту ячейку напрямую,
  не завися от того, виден ли уже B через поиск по ячейкам. Полезно и
  внутри ячейки: клиент узнаёт о переключении на describe, не дожидаясь
  remount.
- **A удалён.** Поиск по ячейкам получает фоллбэк на `<id>-copy`, как у
  SSProxy, но строже: первый проход с `ExactDiskIdMatch`, иначе SSProxy
  каждой ячейки подставит `-copy` сам и выиграет первый ответ; найденный
  `<id>-copy` принимается только если у него есть link на `id` — иначе это
  может быть независимый диск с таким именем. Для живого A фоллбэк не
  срабатывает никогда.

Отсюда инвариант: запись `TLeaderDiskInfo` в состоянии `Principal` на B
сохраняется после финализации — по ней проверяется принадлежность копии.

### 3. Попытка переезда имеет владельца с самого начала

Между созданием B и созданием link у B нет владельца: `LinkUUID` рождается
на A в `CreateVolumeLink`, а условное удаление по fill generation перестаёт
работать после `FinishFillDisk`. Поэтому DM генерирует attempt token до
`Clone`, пишет его в тег B и удаляет B только compare-and-delete по этому
тегу. Тот же token передаётся в `CreateVolumeLink` как `LinkUUID` — тогда
повтор идемпотентен по UUID, а потеря ответа на `CreateVolumeLink` ничего
не теряет.

Чем ограждается:

- A персистит «активная/отменённая попытка» по UUID и отбрасывает поздние
  события отменённой — иначе запоздалый `UpdateFollowerState` заново
  добавляет follower.
- B до сохранения `Following` сверяет UUID из CREATE с attempt token в
  своём теге — иначе CREATE отменённой попытки захватит B новой попытки с
  тем же именем.
- `DestroyVolumeLink` требует UUID и дожидается ответа B: сегодня A
  отвечает после своей транзакции, не ждя follower'а, и результат отмены
  не подтверждает, что B не стал лидером.
- DM держит per-disk owner: пока идёт переезд, `Resize`, `Delete` и вторая
  миграция того же диска отвергаются.

Fill generation при этом остаётся как есть; `FinishFillDisk` вызывается
сразу после `Clone`, до link — защита от чужих записей на время
копирования и так есть: тег `source-disk-id` плюс гейт follower'а, который
пускает только copy-клиентов.

### 4. Мост из таблетки в чужую ячейку

Копирование живёт в таблетке лидера, в `libs/storage`. Ей нужен канал в B
для control (describe, link) и data (записи в follower). Это сервис-актор
`MakeCellProxyServiceId()` в `libs/storage/api`: по `CellId` отдаёт
control-сервис и `IStoragePtr` соединения с ячейкой; реализация в
`libs/cells` поверх `ICellManager::CreateConnection`, регистрируется в
bootstrap рядом с mon-актором ячеек; без ячеек — заглушка.

Соединение — на каждый link, как сегодня на каждый endpoint: мост просит у
`ICellManager` соединение с любым живым хостом B и держит его до конца
копирования или ошибки; при bootstrap data-соединений нет. Живёт оно на
хосте таблетки лидера; после переезда таблетки по hive новый актор заводит
новое и платит за установку первым запросом — приемлемо.

Хост в B — из пула, не хост таблетки follower'а: о хосте таблетки соединение
узнаёт только из ответа на mount, а копирование идёт без маунта. Записи
проходят лишний хоп внутри B (volume proxy выбранного хоста → таблетка), как
и внутри ячейки сегодня. Если это окажется заметно, describe через мост
может отдавать хост таблетки, и мост переедет на него — опция, решается на
этапах 2–3 по замерам.

Альтернатива — переливать данные со стороны endpoint'а, как делает DM, —
отвергнута: копирование уезжает из таблетки, теряется зеркалирование, диск
без endpoint'а переехать не может.

### 5. Control через мост

При `FollowerCellId != LeaderCellId`:

- Оба describe follower'а — в `TCreateVolumeLinkActor` и в
  `TVolumeAsPartitionActor`, который сам описывает назначение перед
  копированием, — идут через мост.
- Пропагация link на follower идёт через мост новым запросом
  `UpdateVolumeLink`, который forward service принимающей стороны
  пропускает по тому же гейту, что `Mount`/`Unmount`/`Describe`. На той
  стороне он попадает в существующий обработчик follower'а.
- Контрольный сервис соединения штампует `CellId` и на эти запросы, не
  только на mount/unmount, иначе forward service их не узнает.
- Удаление старого лидера из чужой ячейки таблетка не делает: источник
  удаляет DM.
- `getlinkstatus` остаётся в A, отдаёт `LinkUUID` и обе ячейки.

### 6. Данные через мост без маунта

`copy-volume-client` сегодня работает только in-process: по сети запись без
маунта отбивает storage service, а не таблетка — таблетка такие записи
принимает, пока у диска нет других клиентов. Проверено по всему пути:
RDMA-target, auth и encryption своей проверки не добавляют. Поэтому:

- storage service пропускает без сессии `WriteBlocks`/`ZeroBlocks`/
  `WriteBlocksLocal` от `copy-volume-client` с `CellId` в заголовках.
  `WriteBlocksLocal` обязателен: именно через него идёт RDMA, а gRPC
  fallback скрыл бы его отсутствие. Данные `WriteBlocksLocal` лежат вне
  protobuf, и в volume proxy их нельзя пропускать как есть — bypass
  конвертирует Local в обычный `WriteBlocks` до proxy.
- `TRemoteStorage` ставит `CellId` и `LinkUUID` в заголовки data-запросов;
  таблетка принимает запись только при совпадении `LinkUUID` с её link.
  Проверка — только для записей с `CellId`: внутриячеечный путь UUID не
  ставит, и общая проверка отвергла бы его.
- `TVolumeAsPartitionActor` при чужой ячейке пишет в `IStoragePtr` моста
  вместо volume proxy. Транспорт — data-канал соединения, RDMA с gRPC
  fallback по конфигу ячейки.

Маунта на follower'е нет: ни сессии в мосту, ни unmount при передаче
лидерства. Это и упрощает мост, и убирает целый класс гонок на рубеже.

### 7. Cutover: состояния и переходы

Рубеж — переход follower'а в `Leader`. До него переезд отменяем, после —
нет. Рубеж проходит NBS сам, как внутри ячейки; DM его только наблюдает.

Зачем нужно больше, чем сегодня. Сегодня лидер по окончании копирования
персистит `DataReady` и сразу шлёт COMPLETED. Зеркальная запись
подтверждается клиенту после ответа обеих сторон, но при fatal-ошибке B
клиенту уходит успех A; ответ клиенту уходит раньше, чем completion
родителю, и если таблетка упадёт между ними, ошибка потеряна. Список записей
в полёте живёт в памяти, и после рестарта сохранённый `DataReady` уходит в
COMPLETED, как будто записей не было. Внутри ячейки окно микросекундное;
между ячейками — сетевой RTT.

Состояния link'а на лидере для межъячеечного переезда:

| Состояние | Записи клиента | Отмена | Переход |
|---|---|---|---|
| `Preparing` | открыты, зеркалируются | да | по окончании фонового прохода → `Draining` |
| `Draining` | `E_REJECTED` | **нет** | список в полёте пуст → `DataReady`; рестарт → `Resyncing` |
| `Resyncing` | открыты, зеркалируются | да | полный фоновый проход → `Draining` |
| `DataReady` | `E_REJECTED` | нет | COMPLETED принят B → `LeadershipTransferred` |
| `LeadershipTransferred` | `E_BS_INVALID_SESSION` + `EF_OUTDATED_VOLUME` | нет | терминальное |
| `Error` | открыты | — | только из `Preparing`/`Draining`/`Resyncing` |

Что это даёт:

- **Drain переживает рестарт.** `Draining` персистентен и стоит *до*
  `DataReady`. Пустой список после рестарта ничего не доказывает (см. выше),
  поэтому из `Draining` рестарт ведёт в `Resyncing`: записи снова открыты,
  фоновый проход идёт по всему диску, затем короткий `Draining` только для
  записей в полёте. Полный проход дёшевым не будет — карта непустых
  диапазонов не персистится, и планировщик её не читает — но записи при
  этом открыты, и пауза остаётся одним drain'ом. Повторный рестарт в
  `Resyncing` начинает проход заново при открытых записях.
- **Барьер стоит на входе в migration actor.** Список в полёте не покрывает
  весь путь: при `TrackUsedBlocks` или light checkpoint запись идёт через
  промежуточный актор и может прийти после того, как список опустел.
  Поэтому после персиста `Draining` любой write/zero, дошедший до
  `TFollowerDiskActor`, отвергается, как бы он ни добрался.
- **Назад в `Principal` после рубежа пути нет.** `Unlink` отвергается с
  `Draining` — `DestroyVolumeLink`, начатый DM по старому статусу, может
  прибыть уже в `Draining`; проверка и отказ в одной транзакции. `Error`
  после `DataReady` запрещён: сегодня `Error` численно старше в enum и
  проходит guard, а `UpdateLeadershipStatus` при `Error` снова считает A
  principal'ом при живом лидере B. Ошибка после рубежа — это «B
  недоступен»: A остаётся в `LeadershipTransferring` и повторяет COMPLETED.
- **Фенсинг.** `DataReady` персистится на A до RPC в B; при восстановлении
  A сверяет состояние B по `LinkUUID`. Порядок фиксации роли (follower
  фиксирует и отвечает, A сохраняет `LeadershipTransferred` после) не
  меняется.
- Числовой guard `newState >= State` для цикла `Draining ↔ Resyncing` не
  годится и заменяется явной таблицей. Для межъячеечного link при
  fatal-ошибке B клиенту уходит ошибка B, а не успех A; внутриячеечное
  поведение не меняется.

`getlinkstatus` отдаёт `Resyncing` как `PREPARING`, `Draining` как
`LEADERSHIP_TRANSFERRING`.

### 8. Рубеж на follower'е и видимость B

На follower'е одной транзакцией localdb — `Leader` плюс пометка «снять
тег». Снятие `source-disk-id` идёт через SchemeShard и в ту же транзакцию
не помещается, поэтому follower доделывает его после рестарта по пометке.
Клиента окно «тег ещё не снят» не задевает: он переключается по
`PrincipalDiskId` + `PrincipalCellId` из describe A, а не через поиск B по
ячейкам. Поиск с фильтром по тегу нужен только новым endpoint'ам, и для
них B должен быть уже виден — DM удаляет A лишь после подтверждения, что
тег снят.

### 9. Старые endpoint'ы и удаление A

После рубежа лидер принуждает клиентов к remount: на IO отвечает
`E_BS_INVALID_SESSION` с `EF_OUTDATED_VOLUME`, а клиентов без IO добирает
таймер remount сессии, который работает с периодом `ClientRemountPeriod`
(4 с). Серверный `InactiveClientsTimeout` (9 с) — другое значение: после
него клиент без remount считается stale и выкинут с A независимо от
переезда.

DM удаляет A, когда выполнены все три условия: на A ноль клиентов, прошло
не меньше `InactiveClientsTimeout` после рубежа, B виден через поиск по
ячейкам. «Ноль клиентов» сам по себе слабый критерий: клиент пропадает из
списка и по обрыву соединения, хотя endpoint ещё держит маршрут в A; а
переключение при ошибке describe B молча прекращает попытку и повторяет её
на следующем remount — отсюда третье условие. Go SDK сегодня отбрасывает
`Clients` из `StatVolume`, хотя в API они есть — нужен метод SDK.

Endpoint, который так и не переключился до удаления A, получит
`E_NOT_FOUND` до следующего рестарта — принято; после рестарта его спасёт
фоллбэк из решения 2.

### 10. Шифрование

KMS один на все ячейки, KEK общий, DEK не привязан к имени диска (ни в
интерфейсе, ни в продовом клиенте). Поэтому B создаётся с тем же
`EncryptionDesc`, что у A: `CreateVolume` принимает готовый
`EncryptedDataKey` и не генерирует новый, `Clone` копирует desc целиком,
после `Clone` DM сверяет desc обеих сторон и останавливается при
несовпадении. Последнее закрывает и auto-KMS: `CreateVolume` включает
root-KMS сам при `NO_ENCRYPTION`, если фича включена для cloud/folder, и
незашифрованный A мог бы получить зашифрованный B. `Ciphertext` в конфиге
уже Base64 — `Clone` не кодирует повторно.

### 11. Что остаётся на стороне DM

- Новый rpc в `PrivateService`; флаг `is_migration_between_cells` на
  публичном `MigrateDisk` — только для старой ветки под флагом конфига.
- Выбранный протокол сохраняется в состоянии задачи, а не читается из флага
  на каждом шаге.
- Прогресс для оператора — `MigratedBytes` из `getlinkstatus`.
- `FINISH_REPLICATION` для этой ветки — ошибка «не применим»: торопить
  таблетку нечем. `FINISH_MIGRATION` не используется, подтверждения
  оператором нет.
- Перед отменой — `getlinkstatus` в A: с `LEADERSHIP_TRANSFERRING` отмена
  невозможна. Источник истины при восстановлении после сбоя — NBS: link в A
  до удаления A, link в B после.

## Порядок работ

Каждый этап сливается отдельно; поведение внутри ячейки не меняется до
последнего. Если код выходит за пределы cells — сначала общая часть с
заглушкой, потом cells.

0. `ShardId → CellId` в link (переименование, схема localdb не трогается);
   заполнение `LeaderCellId`/`FollowerCellId` в `CreateVolumeLink`,
   `DestroyVolumeLink`, `getlinkstatus`; `LinkUUID` и ячейки в ответе
   `getlinkstatus`. Пустой `FollowerCellId` в запросе означает ячейку
   лидера.
1. Мост storage → cells: интерфейс и заглушка, затем реализация.
2. Control через мост; `PrincipalDiskId`/`PrincipalCellId` в describe и по
   всему пути переключения сессии; фоллбэк на `<id>-copy` в поиске по
   ячейкам.
3. Данные через мост без маунта.
4. Cutover по таблице из решения 7. Обязательные тесты: двойной рестарт в
   `Resyncing`; write/zero параллельно полному проходу; обнуление ранее
   непустого на B диапазона; поздний write на входе в `Draining`;
   задержанный `Destroy` на переходе в `Draining`; невозврат A в
   `Principal` после `DataReady`; fatal B → успех A клиенту → crash до
   completion → recovery.
5. Наблюдаемость: текущие переезды на `/blockstore/cells`, сенсоры
   `MovesInProgress`/`MoveFailures`.
6. DM: приватный rpc, attempt token, alias, ожидание перед удалением A,
   метод SDK для `Clients`.

Раскатка: всё из этапов 0–3 должно быть во всех ячейках раньше, чем DM
включит новую ветку — поле в link служит признаком готовности, как
`TabletHost`.

## Риски

1. **Записи по RDMA без проверки источника.** Серверно проверяемого «это
   ячейка A» на RDMA нет, а `LinkUUID` не секрет: он виден на mon-странице
   тома и возвращается в API. Любой, кто имеет сетевой доступ к RDMA-порту
   и читает мониторинг, может писать в follower до передачи лидерства.
   Принято сознательно; закрывается, когда у RDMA-канала появится
   доверенный источник.
2. **Alias в DM** затрагивает каждый вызов NBS по диску, включая placement
   group в обе стороны. Пропуск одного места — обращение к несуществующему
   диску. Нужен полный список.
3. **Состояние разложено по четырём местам**: localdb A, localdb B, теги в
   SchemeShard, статус DM. Протокол задуман так, чтобы сбой между любыми
   двумя шагами восстанавливался от NBS как источника истины; таблица
   переходов и список тестов из этапа 4 — это и есть проверка этого
   свойства.
4. **Полный проход при восстановлении** — ресурсы, сопоставимые с самим
   переездом, хотя и без паузы записей. Дёшево не будет; принято.
